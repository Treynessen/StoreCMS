# Обновление паролей и первоначальной настройки

Реализация для ASP.NET Core 2.2 / MySQL. Новые механизмы не зависят от адреса панели. Рабочая БД и Selectel агентом не менялись. Выполнение нижеследующих действий на рабочем сайте остаётся за владельцем.

## Новая установка

В настройках указать имя целевой MySQL-базы. Если БД отсутствует, приложение автоматически создаёт её; если уже существует, не удаляет и не пересоздаёт. Те же реквизиты проверяются через отдельное подключение без выбранной БД; на нём берётся GET_LOCK для целевого имени и удерживается до конца инициализации. Создание разрешено только после ошибки 1049 (Unknown database) при открытии целевого подключения. Неверный пароль, запрет доступа и недоступность сервера не запускают CREATE DATABASE. Для отсутствующей БД требуются права CREATE DATABASE, для создания таблиц — соответствующие права на целевую БД. При отсутствии права создания выводится отдельная понятная ошибка.

Под той же блокировкой приложение проверяет отсутствие любых таблиц, создаёт схему через EnsureCreated, затем в одной транзакции создаёт роль, admin/admin и маркер SecurityInstallation. У пользователя RequirePasswordChange=true, у новой установки LegacyPasswordResetCompleted=true: legacy-утилита ей недоступна. Для уже открытого целевого подключения используется прежняя блокировка на нём. Вспомогательное подключение и открытое инициализацией целевое подключение закрываются и при успехе, и при ошибке. При повторном использовании DbContext исходные реквизиты берутся из настроек EF: включать PersistSecurityInfo не требуется.

До смены первоначального пароля сервер возвращает только специальную форму и разрешает её отправку и выход. POST/PUT/DELETE остальных действий получают 403. Смена требует текущего пароля, нового допустимого пароля и совпадающего повтора. Существующие ограничения алфавита и минимум 5 символов сохранены; admin в любом регистре запрещён при установке нового пароля во всех сценариях. Для рабочего пароля использовать длинное уникальное значение. После успешной смены сохраняются новый хеш и RequirePasswordChange=false; повторная отправка со старым паролем не может перезаписать результат.

Существующая схема без корректного маркера, неподдерживаемая версия и прерванное создание схемы не считаются новой установкой: запуск прекращается без создания пользователя. Отсутствие/понижение/удаление последнего администратора при наличии маркера ничего не восстанавливает. Не удалять/не обнулять SecurityInstallation для восстановления доступа. После неполного DDL требуется анализ состояния и отдельная процедура восстановления.

Известное прежнее ограничение: составной индекс ConnectedUsers не создаётся на стандартной utf8mb4 MySQL 8 (ошибка 1071). Поэтому только автоматически создаваемой БД задаются utf8/utf8_general_ci, совместимые с текущей моделью. Параметры существующей БД не изменяются; если заранее выделенная пустая БД использует utf8mb4, ограничение индекса остаётся и требует отдельного решения. ALTER DATABASE, удаления таблиц и автоматического обновления старой схемы новый механизм не выполняет. Пересмотр кодировок/индексов остаётся на этапе модернизации.

## Существующий сайт: последовательность владельца

Проверки совместимости (2026-10-16): модель EF не задаёт MaxLength/ColumnType для Users.Password; фактический тип новой схемы Pomelo 2.2 — longtext. Хеш текущего Identity V3 занимает 84 символа. До первого ALTER скрипт UpgradeSecurityV1.sql проверяет фактический столбец через information_schema: допустимы записываемые char/varchar/tinytext/text/mediumtext/longtext вместимостью не менее 84 символов. Бинарные, вычисляемые, отсутствующие и слишком короткие столбцы отклоняются. Скрипт не расширяет и не меняет тип Password автоматически; отказ не добавляет RequirePasswordChange или SecurityInstallation и не меняет записи. Как и при других ошибках скрипта, временная процедура может остаться — требуется проверка, а не слепой повтор.

Непосредственно перед однократной заменой пароля утилита под GET_LOCK повторно проверяет столбец Password и реальные движки Users, ConnectedUsers и SecurityInstallation. Все три должны быть базовыми таблицами InnoDB, поскольку пароль, прежние сессии и маркер изменяются атомарно. При несовместимости выводится понятное сообщение без реквизитов; транзакция изменения данных не начинается. Движки автоматически не преобразуются. Это защищает также от несовместимого изменения схемы после выполнения SQL; требование остановить сайт и не выполнять параллельный DDL сохраняется. При отказе изменение столбца/движков требует отдельного согласования.

1. Сделать проверяемую резервную копию БД и текущего развёртывания. Записать ID существующего администратора и проверить связанные данные. Не передавать агенту legacy-соль или пароль.
2. Остановить **все** экземпляры сайта и фоновые процессы. Старую версию больше не запускать после замены пароля: она не понимает новый формат.
3. На копии БД проверить процедуру целиком. Для рабочего выполнения явно выбрать нужную БД в MySQL-клиенте и выполнить `tools/sql/UpgradeSecurityV1.sql`. Нужны права CREATE ROUTINE, ALTER, CREATE и обычные права изменения данных. Скрипт использует тот же GET_LOCK, что запуск и утилита. Он добавляет только Users.RequirePasswordChange и таблицу SecurityInstallation, записывает версию 1 и LegacyPasswordResetCompleted=false. Пользователей, пароли и связи не заменяет. Скрипт предназначен для однократного применения, не скрывает частично выполненный DDL и не повторяет его автоматически.
4. Собрать/опубликовать приложение и отдельную консольную утилиту SetLegacyAdminPassword с целевой платформой netcoreapp2.2. Полная ASP.NET Identity не требуется. Пакеты и целевая платформа приложения не менялись.
5. Вне репозитория и web-root подготовить временный приватный JSON с секцией DbSettings и строкой ConnectionString для нужной БД; права файла ограничить владельцем. Значение подключения не передавать аргументом команды. Пример формы файла без реквизитов: `{ "DbSettings": { "ConnectionString": "<задать локально>" } }`.
6. Из интерактивного терминала выполнить:

```text
dotnet SetLegacyAdminPassword.dll --connection-file /secure/storecms-maintenance.json --user-id 42
```

`42` заменить на проверенный ID своего администратора. Новый пароль ввести скрыто дважды. Не помещать его в команду, JSON или журналы. Стандартный ввод перенаправлять нельзя. Конфигурацию Selectel утилита не переписывает, приложение и его фоновые службы не запускает.

7. Утилита допускает только существующего пользователя VeryHigh с 32-символьным hex-хешем и незавершённой процедурой. Старый хеш не проверяется и legacy-соль не читается. Под блокировкой в транзакции изменяются Password, RequirePasswordChange и LegacyPasswordResetCompleted; удаляются прежние ConnectedUsers этого администратора. ID, логин, роль, профиль, журналы и остальные связи сохраняются. В случае ошибки перед фиксацией транзакции эти изменения откатываются. После успешной фиксации повторная процедура отказывает, даже если её запустить параллельно. До успешного завершения однократной процедуры новая версия сайта отказывается запускаться: случайный запуск между обновлением схемы и заменой пароля не открывает доступ через прежнюю сессию.
8. Удалить временный файл подключения и исключить утилиту из обычного развёртывания сайта. Запустить новую версию. Проверить вход новым паролем, отказ старого, профиль, список страниц и обычное действие панели на реальном адресе. Сверить ID и связанные данные. Локальная процедура и HTML проверены автоматически; скрытый ввод в терминале владельца и браузер/HTTPS/proxy Selectel требуют проверки владельцем.

DDL MySQL не атомарен. При ошибке обновления не запускать сайт, не удалять маркеры и не повторять скрипт вслепую. Процедура обновления схемы создаётся временно и удаляется после успешного выполнения; при прерывании может остаться StoreCMS_UpgradeSecurityV1, что требует ручной проверки. Откат к старой версии выполнять только согласованно с восстановлением соответствующей резервной копии БД: новый пароль старая версия проверить не сможет.

## Границы этого этапа

Пароли: PasswordHasher<User> Identity V3, PBKDF2-HMAC-SHA256, 600000 итераций, случайная соль 128 бит, метаданные внутри хеша. MD5 для паролей не поддерживается. GetMd5Hash оставлен исключительно для прежнего идентификатора сессии. Cookies, генератор токенов, CSRF и ограничения входа намеренно не изменены. Отзыв прежней сессии реализован только в согласованной однократной процедуре; обычная смена пароля не получила новый механизм отзыва сессий.

Маркер установки не является средством восстановления удалённого администратора. Безопасное дальнейшее восстановление доступа требует отдельного решения владельца; постоянного публичного endpoint сброса нет.
