## Реализация утверждённого варианта A

`Controllers/AdminPanelController/AdminNativePostRedirect.cs` вызывается после action/OnActionExecuted из `AdminAntiforgeryValidation.cs`. Только form POST с Accept text/html (q>0), без X-Requested-With: XMLHttpRequest и с голым StatusCodeResult 200/201 получает 303. Исключения, начатый response, ошибки и другие результаты не преобразуются. Нативная первоначальная смена с её LocalRedirect исключена из карты; прежний 302 сохранён. PUT/DELETE не затронуты.

send_data.js выставляет X-Requested-With: XMLHttpRequest только для POST; это признак формата ответа, не авторизация и не CSRF. Header-only CSRF не мешает признать HTML-запрос нативным; AJAX-маркер без CSRF не пропускает запрос. Accept без явно разрешённого text/html сохраняет прежний короткий ответ. В трёх оболочках обновлён кеш-ключ send_data до 2.3.4-prg; парольная форма и inline DELETE не перерабатывались.

## Историческая причина до исправления

**P2: нативная отправка AJAX-ориентированной формы оставляет POST-документ с пустым ответом и допускает повтор мутации при повторной отправке тела.**

1. `StoreCMS/Views/AdminPanel/UserTypes.cshtml:43`: `method="post"`, `data-admin-ajax`, action отсутствует. Hidden CSRF и pageID=46 находятся в форме; URL документа — `/admin?pageID=9`.
2. При наличии JS обработчик кнопки (`UserTypes.cshtml:71`) и submit-fallback (`Storage/scripts/admin_panel/send_data.js:37`) отменяют нативную отправку. Helper отправляет XHR на origin+pathname без старой query (`send_data.js:116`); callback после 201 перезагружает текущий GET (`UserTypes.cshtml:66`).
3. При отсутствии исполнения JS атрибут data-admin-ajax не имеет встроенного браузерного поведения. Нативный POST идёт на текущий URL с query. Реальный model binding ASP.NET Core 2.2 выбирает form pageID=46 поверх query pageID=9; это проверено обоими направлениями конфликта. Без form-selector query используется как fallback.
4. `AdminAntiforgeryValidation.cs:49` принимает hidden-пару, затем action выполняется. Валидный CSRF в той же сессии не одноразовый и не дедуплицирует бизнес-операции.
5. `AdminPanel(POST).cs:174-177` вызывает AddUserType и возвращает пустой StatusCode(201), без Location/redirect. `DatabaseInteraction/UserType/AddUserType.cs:23-31` каждый раз добавляет новую сущность. Уникальность имени роли не является установленным требованием; добавлять уникальный индекс для обхода проблемы не предлагается.
6. Повтор идентичного POST с действующей сессией/CSRF снова выполняет action. В HTTP-тесте четыре одинаковых POST дали четыре строки; три GET дополнительных строк не дали. Реальный refresh в Opera может потребовать подтверждения повторной отправки — поведение диалога этим HTTP-тестом не установлено.

Оценка P2: неожиданные дубликаты и неясный результат операции при отключённом JS, нарушение целостности/UX. Повышение привилегий, обход авторизации или CSRF не подтверждены. История всех четырёх существующих NoJavaScript_Test не установлена: повтор refresh, повторная ручная отправка или смешанная последовательность не различимы по одному описанию. Эти записи не читались и не удалялись.

## Масштаб

Это объявления, а не число форм после разворачивания foreach и не 37 подтверждённых сценариев дублирования. Отдельная нативная ChangeInitialPassword уже имеет LocalRedirect после успеха.

## Варианты и условие остановки

Пользователь прямо указал: «Если выяснится, что для надёжного устранения проблемы нужны изменения HTTP-контрактов, массовая переработка форм или архитектурное решение, остановись после расследования и представь варианты».

**Предложение A (предпочтительно):** PRG только после успешного нативного POST: 200/201 → 303 с локальным Location → GET. AJAX сохраняет прежние 200/201, headers/body; CSRF и 4xx/5xx остаются настоящими отказами. Нужны явное различение транспорта и безопасный выбор GET-адреса; нельзя слепо доверять Referer/returnUrl или отражать credentials/CSRF в URL. Первоначальный пароль уже имеет нативный redirect; PUT/DELETE не преобразовывать в POST. Это изменение нативного HTTP-контракта, поэтому пока не реализовано. PRG устраняет повтор при обычном refresh финального GET, но не даёт общей дедупликации двойного клика/Back/ручного replay.

**Предложение B:** объявить JS обязательным, показывать явное объяснение и не допускать нативной AJAX-мутации на сервере. Это меняет контракт приёма нативных POST и требует общего правила, сохранив настоящую нативную первоначальную смену. Одного noscript/CSS/onsubmit недостаточно: JS может быть отключён после загрузки или не выполниться из-за ошибки. Наличие X-CSRF-TOKEN не заменяет авторизацию и не является криптографическим доказательством XHR.

Только локальный PRG для роли оставит другие формы с тем же классом дефекта. Уникальный индекс имени роли меняет бизнес-правило; одноразовый CSRF нарушит текущую модель вкладок; Cache-Control: no-store не меняет метод повторной навигации. Эти варианты не рекомендуются.

## После выбора решения

Opera на изолированной фикстуре: JS off, отправка кнопкой и Enter; журнал метода/status/selector без значений секретов; повторные refresh; отсутствие новых строк; затем JS on AJAX 201 и один успех; без/с плохим CSRF 400 без записи; действующая/отозванная сессия; 422/409 не скрываются; выборочные другие POST и PUT/DELETE; нативная первоначальная смена. Отдельно Back/re-submit и отключение JS после загрузки. После реализации необходимы адресная регрессия и независимое ревью исправления. Сейчас к ревью готов диагноз, а не патч.
