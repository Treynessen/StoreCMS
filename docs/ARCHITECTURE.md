# Архитектура StoreCMS

Исторический снимок: 2026-10-14. Ниже в первоначальных разделах — факты на дату аудита, а не описание текущего состояния. Пути относительно корня репозитория; наличие пути в коде не означает наличие файла в рабочей папке.

## Платформа и зависимости

- Решение: `StoreCMS.sln`; единственный проект приложения: `StoreCMS/StoreCMS.csproj`; namespace — `Treynessen`.
- ASP.NET Core MVC/Razor, целевая платформа `netcoreapp2.2`. Точная версия runtime действующего сервера неизвестна.
- Прямые пакеты: `Microsoft.AspNetCore.App` (без явной версии), `Microsoft.AspNetCore.Razor.Design` 2.2.0, `Pomelo.EntityFrameworkCore.MySql` 2.2.0, `SixLabors.ImageSharp` 1.0.0-beta0006.
- Конфигурация выбирает MySQL; `Startup.cs` содержит также ветку SQL Server. Работа SQL Server не проверена.

Все пути таблицы начинаются с `StoreCMS/`.

| Файлы/изображения | `FileManagerManagement/`: каталоги, загрузки, CSS/JS. `ImagesManagement/`: загрузка, размеры/сжатие, производные изображения. `TagHelpers/`: вывод изображений и пагинации |

## Основные взаимодействия

1. **Запуск:** Program → Startup/DI → CMSDatabase. Конструктор контекста вызывает EnsureCreated; Program создаёт роль максимального уровня и пользователя admin/admin, если нет пользователя такого уровня. Это возможно и при последующих запусках. Обязательная смена пароля кодом не обеспечена.
2. **HTTP:** sitemap → forwarded headers → принудительный GC → статика → MVC (`Startup.cs`). `/search` идёт в SearchPage; catch-all с RequestConstraint ищет опубликованную страницу/редирект; далее `/admin`; последняя catch-all ветка — 404.
3. **Публичная страница:** RequestConstraint → MySQL через EF → RequestedPage/Redirection в HttpContext.Items → PageController → шаблон Razor или содержимое. Категория/поиск отдельно получают товары; посещения записываются в БД.
4. **Админка:** диспетчер по HTTP-методу и PageId → проверка сессии/уровня (вход — отдельная ветка) → функции управления → EF/файлы/журнал → HTTP-ответ. Данные для представлений часто передаются через HttpContext.Items.
5. **Шаблон:** исходный текст в сущности Template/Chunk → замена маркеров/условий/ссылок → файл .cshtml → Razor. Генерация использует общий static-список; некоторые операции чанков запускают параллельные ветки с одним DbContext.
6. **Фоновая задача:** Timer → новый DI scope → архив событий пользователей в XML → удаление перенесённых записей → очистка посетителей.

## Хранилища и границы

- `StoreCMS/Settings/config.json`: БД, уровни доступа и настройки поведения; содержит секрет подключения — значения не документировать.
- `StoreCMS/Storage/`: фактический web-root, публичные файлы. `wwwroot` указан в csproj, но Program выбирает Storage.
- `StoreCMS/Views/Templates/`, `Views/Chunks/`: пути генерируемых представлений; `Settings/product_block.cshtml`: вычисляемый путь блока товара. Его наличие не подтверждено текущим деревом.
- `StoreCMS/Logs/`: ошибки и архивы админских событий, путь вычисляется расширениями.
- БД и файловая система изменяются раздельно; единой атомарной фиксации операций нет. DbContext зарегистрирован scoped; конфигурация scoped; фон создаёт свой scope.

## Не установлено

Версия/DDL/collation/FK MySQL, production runtime, Nginx/HTTPS, права файлов, процесс публикации и runtime-компиляция Razor. Миграции, SQL-схема, автоматические тесты и CI-файлы при аудите не найдены. Эти сведения требуют отдельной проверки; устройство кода их не доказывает.

## Историческое дополнение 2.3.2 - выдача antiforgery, 2026-10-17

Базовый снимок выше исторический. В текущем фрагменте Startup регистрирует штатный IAntiforgery ASP.NET Core 2.2 через Security/AdminAntiforgery.cs. Отдельная cookie StoreCMS.Antiforgery.v1: Secure Always, HttpOnly, SameSite=Lax, Path=/, Domain отсутствует, сессионный срок. Имена session/antiforgery раздельны. HTTP-guard и no-store контроллера действуют до Razor.

IAntiforgeryAdditionalDataProvider возвращает версию и SHA-256 предъявленной канонической StoreCMS.Session.v2 либо anonymous-маркер. Значение помещается внутрь защищённого штатного request-token. Provider не аутентифицирует, не обращается к БД, не меняет скользящий срок и не вводит абсолютный срок. Сохраняются D08/D09; отзыв в БД закрывает доступ даже при криптографически валидной остаточной паре.

Views/AdminPanel/_Antiforgery.cshtml выдаёт meta request-token трём оболочкам: LoginForm, CommonPage, ChangeInitialPassword. В изменяющих формах явный Html.AntiForgeryToken и method=post, в GET-формах токена нет. Общие send_data/send_file и inline logout передают X-CSRF-TOKEN; FormData и бизнес-параметры сохранены. После изменения авторизации токен получается полным GET. Старая вкладка после нового входа требует ручного обновления; автоматического повтора мутаций нет.

На дату 2.3.2 обязательная проверка CSRF не была включена (позднее включена по D14): этот исторический фрагмент готовит выдачу и передачу для независимого ревью 2.3.2. Тестовая проверка пары существует только в отдельном host tests/AdminAntiforgeryRegression, не в action приложения. Изображения через GET, публичная статистика, платформа, SQL и хранение сессий не изменены.

## Актуальная архитектура — 2026-10-20

Подтверждено по текущим исходникам и HEAD `512af66`; результаты прежних прогонов и границы приёмки — в [PROGRESS.md](PROGRESS.md). Первоначальный снимок 14 октября и дополнение 2.3.2 выше сохранены как история.

- **Платформа пока прежняя:** netcoreapp2.2, EF Core/Pomelo и MySQL. .NET 10 / ASP.NET Core 10 / EF Core 10 и PostgreSQL/Npgsql — принятая цель D03; основное приложение пока не перенесено. Актуальная очерёдность — [D18](DECISIONS.md#d18) и [D20](DECISIONS.md#d20).
- **Первоначальная настройка:** Program вызывает MySqlSecurityInstallation.Initialize; EnsureCreated удалён из конструктора CMSDatabase и выполняется под GET_LOCK при защищённой инициализации. Новая пустая схема получает admin/admin, RequirePasswordChange и постоянный SecurityInstallation; остальные действия запрещены до серверной смены. Повторный запуск/удаление администратора не восстанавливают стандартный аккаунт. Существующая схема требует явного SQL и однократной локальной legacy-замены с сохранением ID/связей. Проверки вместимости Password и InnoDB не преобразуют несовместимую схему автоматически (D04–D07). Риск захвата первого входа известными реквизитами остаётся.
- **Пароли:** PasswordHasher<User> Identity V3, PBKDF2-HMAC-SHA256, 600000 итераций, случайная индивидуальная соль; старый MD5 не принимается при входе. Полная Identity не внедрялась. См. Security/SecurityFunctions/GetPasswordHash.cs и LegacyPasswordReplacement.cs.
- **Сессии и cookies:** SessionToken/SessionStore хранят в ConnectedUsers SHA-256 от случайного 32-байтового токена; AdminSessionPolicy использует UTC и скользящий IdleTime без обязательного абсолютного предела 8 часов. StoreCMS.Session.v2 имеет Secure/HttpOnly/SameSite=Lax, host-only Path=/; панель требует HTTPS и no-store. Смена пароля отзывает сессии атомарно с обновлением пароля. По D09 запоздавшие ответы не удаляют общую auth-cookie: остаточный отозванный токен не даёт доступа. Сценарий покупателей/refresh не реализован.
- **CSRF уже обязателен:** AdminAntiforgery выдаёт отдельную защищённую cookie и request-token с привязкой к хешу предъявленной session-cookie либо anonymous. AdminAntiforgeryValidation.cs вызывает IAntiforgery.ValidateRequestAsync для изменяющих методов, включая вход/выход, после HTTPS/сессии/селектора/bootstrap/прав и до action. Недействительная пара даёт пустой 400; приоритеты 401/403 сохранены. Binding и служебная сессионная работа предшествуют проверке. Hidden/meta и X-CSRF-TOKEN передаются формами/XHR; старая вкладка после нового входа требует GET, автоматического повтора нет (D12/D14).
- **PRG:** AdminNativePostRedirect.cs преобразует голый успешный 200/201 нативного POST с Accept text/html и без X-Requested-With: XMLHttpRequest в 303 к GET по явной карте 26 селекторов. Сохраняются AJAX-контракты и ошибки. Это не общая идемпотентность (D15).
- **Изображения:** ProductImageOperations/Coordination используют именованный Mutex по каноническому каталогу. DELETE получает фактическое имя и защищённый снимок/версию набора из App_Data; устаревший/подменённый набор даёт 409 до удаления. После удаления уплотняется фактический список. Upload готовит JPEG во временных файлах и публикует законченный оригинал File.Move без перезаписи, затем сохраняет метаданные. По IR-01/D17 при ошибке после публикации оригинал остаётся, успех не объявляется, finally очищает временные файлы. Блокировка охватывает согласованные операции и ImageTagHelper, проверена между процессами одного сеанса ОС; общей транзакции БД/ФС и распределённого lock нет (D16/D17).
- **Шаблоны:** список замен теперь локален рендеру; AddChunk/EditChunk/DeleteChunk перегенерируют последовательно с одним DbContext. Общий static-список и параллельные ветки из снимка 14 октября исправлены в подтверждённом объёме пунктов 13/14 аудита.

**Сохранённые ограничения:** монолит MVC/Razor, partial-диспетчеры, статические операции EF/файлы/журналы и HttpContext.Items; отдельные фиксации БД и файлов, агрегатные гонки alias/удаления, неполное восстановление после сбоев. Images и ImageTagHelper сохраняются. Конструктор ImageHandler по-прежнему может удалять метаданные/производные при отсутствии оригинала во время GET; D16 допускает автоматическую сверку, но не закрывает дефекты F-IMG-03/04/05/06. Нет общего допуска тяжёлой обработки изображений; актуальность размеров/кеша и безопасность публикации миниатюр требуют оценки. Исследования памяти и отказа от Images не являются реализованной архитектурой.

## E0.1 - адресная публикация Razor, 20.10.2026

`WriteCshtmlContentToFile` нормализует полный путь, согласует writers одного пути внутри процесса и удаляет неиспользуемые записи блокировок. Уникальный `.tmp` в том же каталоге полностью закрывается до публикации. Windows использует MoveFileExW/REPLACE_EXISTING без межтомного копирования, с ограниченным повтором конфликтов доступа; ветка Linux - File.Replace/File.Move. Удаление final перед публикацией не выполняется; finally очищает только собственный временный файл. Прямой StreamWriter в product_block и rename/delete Template/Chunk этим не защищены. Замена публикует новый файл, сохранение прежних индивидуальных ACL/атрибутов не гарантируется.

CR/LF в обычном C# string literal условий экранируются после backslash/кавычек; Html.Raw и синтаксис маркеров сохранены. Проверены Windows, runtime 2.2.8 и published-host 10.0.13; Linux, сетевые ФС и аварийная долговечность NOT TESTED. Локальная блокировка не защищает несколько процессов/серверов и разные пути к одному объекту через ссылки. AddTemplate/AddChunk публикуют файл до SaveChanges; EditTemplate/EditChunk сохраняют БД раньше файлов. Нет общей транзакции БД/ФС, атомарного обновления набора файлов или гарантии порядка пользовательских версий. Основная платформа прежняя; P04 о Runtime Compilation - отдельное неутверждённое предложение. Подробности: `tests/RazorPublicationRegression/README.md` и отчёт E0.1.

**Границы знания:** появились SQL-инструкции обновления и адресные тестовые наборы (см. PROGRESS.md); автоматические миграции на PostgreSQL не реализованы. Production-схема, proxy/HTTPS/Data Protection, права диска, нагрузка, восстановление и полный браузерный CRUD не объявляются проверенными. Актуальные открытые вопросы — в [AUDIT.md](AUDIT.md#current-register).

## Целевая архитектура и будущий перенос данных — D20

Текущая MySQL обслуживает прежнее приложение; целевая PostgreSQL предназначена для обновлённого StoreCMS на .NET 10 / ASP.NET Core 10 / EF Core 10 через Npgsql. После E0 сначала модернизируется приложение и создаётся рабочая схема PostgreSQL. Разработка и полноценное тестирование выполняются на отдельной тестовой PostgreSQL с тестовыми данными; создание такой среды здесь не заявляется выполненным.

Целевая схема должна поддерживать последующий перенос важных данных, идентификаторов и связей, но не обязана полностью повторять MySQL. Проверка SQL/LINQ, типов, ключей, ограничений, индексов, collation и миграций схемы остаётся частью модернизации приложения.

По [D20](DECISIONS.md#d20) после завершения разработки и тестирования создаётся отдельная .NET-программа переноса с соответствующими провайдерами MySQL и PostgreSQL. Она переносит необходимые данные с сохранением важных ID, связей и целостности; при переносе учитываются Storage и ссылки на файлы. Сейчас мигратор, пробный перенос, подробное исследование содержимого существующих данных и перенос Storage не выполняются. Финальный перенос, проверка результата и переключение выполняются отдельным этапом с разрешения пользователя.
