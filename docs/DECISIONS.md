# Технические решения

Статусы: **принято** — подтверждено владельцем; **предложено** — обсуждается; **историческое** — поведение кода, не новое одобрение. Дата первоначальных исторических решений неизвестна.

| ID | Статус | Решение / основание | Последствия |
|---|---|---|---|
| D01 | Принято, 2026-10-14 | В этой задаче создать компактную документацию без изменений исходного кода | Факты и предложения разделять; ссылаться на файлы вместо копирования кода |
| D02 | Принято как предпочтение владельца, 2026-10-14 | Первоначальная настройка БД/администратора должна быть автоматической, без ручного создания пользователя SQL-командами | Владелец объяснил admin/admin как временный вход для последующей смены. Это предпочтение удобства; безопасная реализация ещё не выбрана |
| D03 | Принято, 2026-10-15 | По решению владельца целевой стек модернизации: .NET 10, EF Core, PostgreSQL через Npgsql; MySQL заменяется PostgreSQL | Перенос выполнять на этапе модернизации .NET, не сейчас. До него продолжать критические исправления существующего приложения; не менять ради переноса DbContext, зависимости, SQL, подключение или схему. Версии PostgreSQL/EF Core/Npgsql и план миграции уточнить при реализации |
| D04 | Принято, 2026-10-15 | Новая установка автоматически создаёт admin/admin; до серверной обязательной смены пароля остальные функции запрещены. В ранее инициализированной базе стандартный аккаунт не восстанавливается. Современные солёные парольные хеши без полной Identity и без legacy-миграции при входе | Существующему администратору — отдельная безопасная однократная установка пароля с сохранением ID/связей, без чтения legacy-соли. Не привязываться к /admin. Рабочую БД/Selectel не менять; cookies/токены/CSRF/ограничения входа — следующие задачи |
| D05 | Принято, 2026-10-15; владелец подтвердил весь план | SecurityInstallation + Users.RequirePasswordChange; EnsureCreated только в защищённом запуске, GET_LOCK и атомарная фиксация bootstrap; явный SQL для существующей схемы; локальная консольная однократная замена legacy-пароля по ID и удаление прежней сессии в одной транзакции | Новая только пустая схема, существующая без маркера/неполная останавливается. Таблица/флаг/утилита реализованы и испытаны только на собственных одноразовых тестовых БД. Новые хеши — PasswordHasher<User> Identity V3, 600000 итераций. Production обновляет владелец по ADMIN_SECURITY_UPGRADE.md |
| D06 | Принято, 2026-10-15; восстановление поведения явно запрошено владельцем | Отсутствующая MySQL-база снова создаётся автоматически. Инициализация держит GET_LOCK через подключение без выбранной БД с теми же реквизитами; CREATE допустим только после 1049 целевого подключения | Именование блокировки, EnsureCreated, маркер и запрет повторного bootstrap сохраняются. Только новой БД задаются совместимые utf8/utf8_general_ci из-за прежнего индекса ConnectedUsers; существующие кодировки и данные не меняются. Неверные реквизиты/права/недоступность не считаются отсутствием БД. Selectel не изменяется |
| H01 | Историческое, подтверждено кодом | Монолит MVC/Razor + EF; MySQL выбран настройкой; исходный стек netcoreapp2.2 | `StoreCMS/StoreCMS.csproj`, `Startup.cs`, `Database/Context/CMSDataBase.cs` |
| D07 | Принято, 2026-10-16; явно запрошено владельцем по ревью 2.1 | До обновления проверять фактическую вместимость и текстовый тип Users.Password для 84-символьного хеша; перед legacy-заменой требовать InnoDB у таблиц транзакции | Безопасный отказ без изменения записей; столбец и движки автоматически не преобразуются. Runtime повторно проверяет Password и все три таблицы транзакции: Users, ConnectedUsers, SecurityInstallation. Дальнейшие изменения несовместимой схемы требуют отдельного согласования |
| H02 | Историческое, заменено D04/D05 | Ранее EnsureCreated вызывался в контексте; admin/admin создавался при отсутствии пользователя максимального уровня без принудительной смены | Старое поведение удалено на втором этапе |
| P01 | Историческое предложение, заменено D04/D05 | Ранее предлагался одноразовый код первого запуска | Владелец выбрал admin/admin с обязательной серверной сменой и отдельно подтвердил схему/однократную процедуру |
| P02 | Предложено | Сначала исправить удаление изображений и гонки шаблонов, затем вход/пароли/CSRF, после — платформу | Порядок предложен после аудита; реализация и окончательная очерёдность не утверждены |
| P03 | Предложено; целевой стек определён D03 | Переносить постепенно, сохраняя модульный монолит, URL и данные | Подход к переносу, миграции и публикация шаблонов ещё не утверждены; выбор СУБД/провайдера больше не открыт |

Для нового решения записывать: ID, дату, статус, выбор, короткую причину и последствия. Изменение предложения на «принято» должно опираться на явное согласование. Совместимость версий проверять заново при реализации.

При дальнейшем планировании учитывать D03. Работы, целесообразные только при переходе на PostgreSQL, отмечать отдельно в PROGRESS.md как «на этап переноса», чтобы не выполнять их дважды. Это не основание откладывать необходимое устранение критического дефекта текущего приложения. Рекомендации по MySQL в AUDIT.md отражают исходный аудит, а не новый целевой стек.
