# Подэтап 2.2: административные сессии

## Принятая политика

`SessionToken`, `SessionStore` и `SessionCookies` отвечают за случайный секрет, SHA-256, серверное хранение, транзакции и cookie. `ISessionPolicy` отделяет правила истечения и продления; существующая административная точка входа выбирает `AdminSessionPolicy`. Выбор политики не выводится из числового уровня роли. Будущая покупательская авторизация сможет использовать отдельную политику и точку входа; регистрация, новые категории пользователей и refresh-инфраструктура сейчас отсутствуют.

У администратора одна текущая сессия на UserID. Срок скользящий: `UTC now - LastActionUtc < User.IdleTime`; на точной границе сессия истекает. Фиксированного абсолютного ограничения нет. При непрерывной работе авторизация сохраняется дольше 8 часов и суток. Изменение IdleTime действует на следующую проверку. MySQL `datetime(6)` не хранит зону; приложение записывает UTC и интерпретирует прочитанные значения как UTC.

В просмотренных Razor-представлениях и `Storage/scripts/admin_panel` нет периодического опроса/heartbeat. Большинство AJAX запускается кликом или выбором файла, GetVisitors — кнопкой. Исключение: UserProfile.cshtml:147-148 и UserActions.cshtml:40-41 однократно вызывают getLogButton.click(), если исходная коллекция журнала пуста. Этот дочерний GET относится к открытию страницы и продлевает IdleTime; ручная подгрузка также продлевает срок. Javascript и обработчики не менялись. Статические ресурсы не проходят аутентификацию панели. HEAD, OPTIONS и помеченная Purpose/Sec-Purpose предзагрузка не продлевают LastActionUtc. Простое чтение/движение мыши без запроса не продлевает сессию. Сервер не доказывает присутствие человека: при будущем добавлении автозапросов их нужно явно исключить из административной политики, а не использовать как keep-alive.

Для покупателей в будущем предполагается отдельное «Запомнить меня» с долгоживущими отзывными токенами, например 30 дней. Сейчас нет таких cookies, сроков, таблиц или полей. Лимиты администратора не зашиты в низкоуровневое хеширование/хранилище.

## Что меняется

- Cookie `StoreCMS.Session.v2`: 32 случайных байта CSPRNG в каноническом Base64Url. В ConnectedUsers хранится только SHA-256 исходных байтов (`char(64)`, ASCII, `ascii_bin`). Значение из БД не является принимаемым cookie.
- HttpOnly=true, Secure=true, SameSite=Lax, host-only, Path=/; без Expires/MaxAge. Закрытие браузера не гарантирует удаление cookie, поэтому серверный idle timeout остаётся обязательным.
- IPAdress/UserAgent сохраняются только для диагностики входа (45/255 символов), не ограничивают доступ. Смена сети/UA не вызывает выхода; украденный действующий cookie может использоваться с другого IP. Компенсирующие меры: CSPRNG, HTTPS, HttpOnly, idle timeout и серверный отзыв. Это не защита от XSS/CSRF/вредоносного ПО.
- Смена обычного и первоначального пароля атомарно удаляет все сессии пользователя; после успеха требуется новый вход. Правка профиля без NewPassword сессию сохраняет. Legacy-процедура 2.1 сохраняет прежние правила и удаляет сессию без зависимости от новых имён колонок.
- Выход удаляет только предъявленный TokenHash и очищает только legacy-cookies userName/loginKey; повторный выход возвращает 200. Ошибка БД не выдаётся за успешный отзыв.
- Для административных ответов выставляется no-store; HTTP-запросы панели получают 403. URL панели не зашит в политику, работают пользовательский маршрут и PathBase.

## Результат отзыва и отказ аудита (F-01/F-02)

Проверка недействительного/истёкшего токена, logout и обе смены пароля не посылают удаление `StoreCMS.Session.v2`. Удаление cookie по общему имени не сравнивает её значение: ответ по A мог бы стереть B, полученную от нового входа раньше прихода этого ответа. Отзыв в БД остаётся обязательным и атомарным; старый токен всегда отвергается. Отозванная HttpOnly-cookie может оставаться у клиента до нового входа/завершения браузерной сессии, но не даёт доступа. Следующий успешный вход заменяет её. Не добавлять автоматический Clear при отказе аутентификации. Перестановка двух успешных входов с разными Set-Cookie остаётся ограничением одной текущей сессии и требует отдельной проверки/координации клиента, если станет продуктовым требованием.

События успешного входа и изменения профиля записываются после commit через TryAddCommittedAdminPanelLog. Ошибка БД только этого необязательного события не меняет успех основной операции на 409; неуспешная добавленная запись отсоединяется от EF, в ILogger отправляется обезличенное событие 2202. Пароль и отзыв фиксируются прежней общей транзакцией. Исключения до commit по-прежнему обрабатываются штатно, остальные вызовы журналирования не менялись. Журнал не имеет гарантии доставки: при отказе событие может потеряться; очередь/outbox и обязательный транзакционный аудит не вводятся. Исключение провайдера/SQL/текст события в диагностике не выводятся.

## Конкурентность

Выдача, проверка/продление, смена пароля и выход используют короткие транзакции ReadCommitted с единым порядком блокировок Users → ConnectedUsers. Блокировка строки Users работает между процессами, а не только внутри одного сервера. При выдаче после проверки пароля под блокировкой повторно сравнивается актуальный парольный хеш: устаревший результат не может создать сессию после смены пароля. Криптографические вычисления пароля выполняются до блокировки.

Продление меняет только LastActionUtc и не перезаписывает TokenHash/профиль. Выход/удаление по хешу не удаляет заменившую его сессию. UTC для проверки обычного HTTP-запроса берётся после ожидания блокировки. Уже авторизованный исполняющийся запрос не отменяется задним числом. При нарушенной синхронизации часов/будущем LastActionUtc доступ закрывается; часы всех экземпляров должны быть синхронизированы.

## HTTPS и proxy перед обновлением

На клиентском участке требуется HTTPS для всей панели, включая форму входа и передачу пароля. HTTP должен перенаправляться на HTTPS на границе до ввода credentials либо отклоняться. Secure-cookie не шифрует форму, уже отправленную по HTTP.

UseForwardedHeaders вызывается до middleware, использующих схему/IP. Сохраняются безопасные штатные ограничения ASP.NET Core 2.2: доверены loopback proxy и одна пересылка. Не очищайте KnownProxies/KnownNetworks и не доверяйте произвольному X-Forwarded-Proto. Если Nginx находится не на loopback, до публикации нужно явно настроить его точный доверенный адрес/сеть в ForwardedHeadersOptions и проверить реальную топологию. Заголовки от недоверенного клиента не должны разрешать HTTP-вход. HSTS для всего хоста и конфигурация production-Nginx автоматически не менялись.

Для локальных проверок используется HTTPS Kestrel с одноразовым тестовым сертификатом. Исключение проверки сертификата существует только в тестовом HttpClientHandler.

## Явное обновление MySQL

Рабочую БД обновляет владелец после проверки резервной копии. Приложение не запускает ALTER автоматически.

1. Убедиться, что 2.1 завершён: SchemaVersion=1, LegacyPasswordResetCompleted=1, современный пароль уже установлен. При переходе с legacy сначала выполнить прежнюю инструкцию ADMIN_SECURITY_UPGRADE.md и однократную замену пароля, затем 2.2. Старый формат ConnectedUsers остаётся поддерживаемым локальной legacy-операцией отзыва.
2. Сделать резервную копию и проверить восстановление. Остановить все экземпляры и исключить фоновые обращения старой версии. GET_LOCK защищает процедуру запуска, но не заменяет остановку старых серверов.
3. На обезличенной копии проверить реальную схему/индексы/FK, движки, версию сервера, права и кодировки. SQL рассчитан на исходную семиколоночную таблицу с четырьмя varchar(255), LastActionTime datetime, целочисленными ID/UserID и ожидаемыми связями. Другие варианты останавливаются без автоматического исправления.
4. Выбрать нужную БД и выполнить `tools/sql/UpgradeSessionsV2.sql` клиентом, поддерживающим DELIMITER. Нужны SELECT/DELETE, ALTER/INDEX, CREATE ROUTINE/ALTER ROUTINE/EXECUTE и доступ к метаданным. Не передавать пароль в аргументах/логах.
5. Скрипт до удаления данных проверяет InnoDB Users/ConnectedUsers/SecurityInstallation, маркер 2.1, вместимость Users.Password, идентификаторы, уникальный UserID, FK и отсутствие входящих ссылок на сессии. Перед DELETE также проверяет свободное имя IX_ConnectedUsers_TokenHash, единственный полный старый индекс, простой PK, дополнительные индексы удаляемых полей/неподдерживаемые префиксы IP/функциональные индексы, дополнительные FK, CHECK и триггеры. При несовместимости — отказ без изменения строк; пользовательские индексы и ограничения не удаляются автоматически. Затем удаляет только ConnectedUsers и одним ALTER заменяет поля/индекс. Все прежние сессии отзываются; пользователи/пароли/роли/журналы/маркер не меняются.
6. Итог: ID, UserID, TokenHash, LastActionUtc, IPAdress, UserAgent. Уникальные TokenHash и UserID. Нет UserName/LoginKey/LastActionTime, CreatedUtc, абсолютного срока и покупательских полей. Новый EnsureCreated создаёт тот же формат, включая utf8mb4. Charset существующей БД и D06 не меняются.
7. Поставить новую сборку и запустить. Проверка схемы сессий выполняется отдельно от Validate маркера 2.1; несовместимость останавливает запуск без bootstrap/DDL. Проверить HTTPS, вход, принудительную смену для новой установки, роли/обычные действия, смену пароля, выход и повторное предъявление старого токена.

Повтор успешно завершённого SQL не удаляет новые сессии. При ошибке процедура может остаться: после выяснения причины удалить только служебную процедуру `StoreCMS_UpgradeSessionsV2`, затем повторить проверку/запуск. Частичная или нестандартная схема отклоняется; не сбрасывать SecurityInstallation. DDL MySQL имеет неявные commit: rollback всей процедуры не гарантируется. Если DELETE уже завершился, старые сессии восстановить нельзя и не нужно.

Откат: остановить сайт; восстановить совместимую структуру только ConnectedUsers пустой, затем прежние бинарные файлы. Не откатывать актуальные Users.Password/маркеры из старого резерва ради сессий. Порядок восстановления заранее проверить на копии. Смешанное обслуживание одной БД старыми/новыми бинарными файлами запрещено.

## Проверки и оставшиеся границы

Адресные регрессии F-01–F-04 находятся в tests/SessionReviewRegression: безопасная изоляция внутри существующей локальной test по AGENTS.md, настоящие HTTPS-ответы с управляемым порядком, отказы post-commit-аудита, preflight SQL и UTC/IdleTime. Подробности и команды — README набора. HTTP-host вызывает production-методы, но не запускает полный MVC/Razor/Startup и Javascript браузера.

Прежние автоматические сессионные сценарии находятся в tests/AdminSecurityIntegration/SessionChecks.cs (`--sessions-only`); общий набор 2.1 адаптирован к HTTPS, одной cookie и повторному входу после смены. `--sessions-only` требует отдельный временный сервер: создаёт и удаляет только изначально отсутствовавшую test и собственные storecms_security_test_<GUID>. Он отказывается использовать уже существующую test. Реквизиты берутся из отдельного файла; хост принудительно 127.0.0.1, порт — из явно переданных тестовых настроек. Не использовать production-конфигурацию.

CSRF, rate limit и XSS — отдельные задачи аудита, не считаются устранёнными подэтапом 2.2. Ручная проверка браузера и реального HTTPS/proxy рабочего развёртывания нужна перед публикацией. Коммит и push требуют отдельного распоряжения владельца.
