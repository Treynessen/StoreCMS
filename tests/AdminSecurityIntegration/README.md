# Интеграционные проверки второго этапа

2026-10-16: после проверок фактической совместимости хранилища — **120 проверок прошли** на MySQL 8.0.40 / runtime 2.2.8 (прежние 65 + 55 новых). Реальная новая схема имеет Users.Password типа longtext. Дополнительно проверяются varchar(32/83/84/85), char(84), text/longtext и varbinary(84), неизменность типа/длины при SQL, отказ до добавления защитных столбца/таблицы, сужение Password после SQL, InnoDB и реальные MyISAM-копии Users/ConnectedUsers/SecurityInstallation. При отказах сравниваются все поля синтетических записей пяти таблиц, включая пароль, сессию и маркер; снимки хранятся только в памяти. MyISAM-копии создаются без внешних ключей, у копии ConnectedUsers убран длинный составной индекс только для совместимости с пределом MyISAM. Исходная схема не меняется. Собственные временные базы и учётная запись очищены.

Настоящие MySQL, EF Core/Pomelo и ASP.NET Core 2.2 MVC/Razor/Kestrel. Базы `test`, `test_db`, рабочая БД и настройки сайта не изменяются. Набор использует только собственные случайные `storecms_security_test_<GUID>` на **127.0.0.1:3306**: имена проверяются как отсутствующие до теста; базы создаются фикстурой либо самим приложением и удаляются в finally. Основные схемы используют utf8/utf8_general_ci. Отдельная база служит проверкой прежнего EF-создания. Для отрицательных сценариев создаётся одна временная учётная запись с SELECT только на собственной тестовой базе; в finally удаляется только эта успешно созданная запись. Нужны локальные права root на базы и CREATE USER/GRANT. При аварийном завершении процесса остатки нужно проверить вручную. Запуск разрешается только владельцем локального тестового сервера.

Пароль локального MySQL читается в память из приватного JSON через `--credential-config`; ожидается DbSettings:ConnectionString с UserID=root. Хост, порт и база из файла не используются. Секреты не копируются и не выводятся. Для тестов нельзя использовать реквизиты production или размещать файл в Git. Ни приложение Program.Main, ни производственные таймеры/логгер не запускаются. Сайт для проверки использует реальные контроллеры и Razor с маршрутом `/private/control-room`; подключение передаётся в DI только в памяти. Безопасный файл тестовых настроек содержит лишь пустую секцию уровней, без реквизитов.

```powershell
dotnet restore tests/AdminSecurityIntegration --configfile tests/AdminSecurityIntegration/NuGet.Config -p:RestoreFallbackFolders="$env:USERPROFILE/.nuget/packages" -p:NuGetAudit=false
dotnet build tests/AdminSecurityIntegration --no-restore
dotnet tests/AdminSecurityIntegration/bin/Debug/netcoreapp2.2/AdminSecurityIntegration.dll --credential-config <приватный-json> --source-root <корень-репозитория>
```

При проверке приложение собиралось в отдельной копии исходников без секретной конфигурации через `-p:ProductionProject=<изолированная-копия>/StoreCMS.csproj`; результаты сборки рабочего приложения не перезаписывались. Нужны .NET/ASP.NET Core runtime 2.2, SDK и кеш пакетов.

Проверяются: пустая база, четыре параллельных процесса инициализации, повторные запуски; единственность администратора/маркера; сохранение хеша; параллельные HTTP-хосты; вход admin/admin, серверные запреты POST/PUT/DELETE, обязательная форма на произвольном URL, неверный текущий пароль/повтор/admin; успешная смена, обычные страницы/операция/профиль/выход и повторный вход новым паролем; конфликт двух старых контекстов при смене; удаление/понижение администратора без восстановления; отказ старой/неполной/неподдерживаемой схемы; выполнение настоящего UpgradeSecurityV1.sql на legacy-фикстуре; сохранение ID=42/профиля/роли/журнала; одноразовость и параллельность замены, отказ неправильного ID/admin и удаление прежней сессии. Legacy-хеш синтетический, производственная соль не нужна.

Это автоматические HTTP-проверки с настоящими Razor, а не ручная проверка браузера. Консольный ввод и раскладка/HTTPS/proxy рабочего сервера проверяются владельцем отдельно. EOL платформы и старые риски cookies/CSRF/token/rate-limit остаются отдельными задачами.
