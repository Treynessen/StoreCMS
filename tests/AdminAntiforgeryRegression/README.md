# Выдача и передача antiforgery, 2.3.2

Набор для ASP.NET Core 2.2.8 проверяет настоящие IAntiforgery/AdditionalDataProvider, Razor и AdminPanelController. Обязательной проверки CSRF на рабочих action пока нет. `/__csrf_probe` существует только в тестовом host и вызывает ValidateRequestAsync для проверки переданной пары без бизнес-операций.

## Запуск

Собирать в изолированной копии StoreCMS и tests без config.json, bin/obj/.vs; сохранить относительную структуру каталогов. Нужны установленные runtime 2.2.8, SDK, Node.js, локальный кеш NuGet и существующая MySQL test. NuGet.Config отключает сетевые источники. Пример из корня копии:

```powershell
dotnet restore tests/AdminAntiforgeryRegression --configfile tests/AdminAntiforgeryRegression/NuGet.Config -p:NuGetAudit=false -p:RestoreFallbackFolders="$env:USERPROFILE/.nuget/packages"
dotnet build tests/AdminAntiforgeryRegression --no-restore
dotnet tests/AdminAntiforgeryRegression/bin/Debug/netcoreapp2.2/AdminAntiforgeryRegression.dll <исходный-корень-StoreCMS>
node tests/AdminAntiforgeryRegression/client.js <исходный-корень-StoreCMS>
node tests/AdminHttpErrorRegression/client.js <исходный-корень-StoreCMS>
```

Аргумент исходного корня нужен для чтения AGENTS.md и реальных JS/Razor, не config.json. ContentRoot направлен на изолированную StoreCMS; Razor также скомпилирован в сборку. Data Protection в тесте ephemeral; сертификат одноразовый, проверка сертификата отключена только тестовым клиентом. Production Program/Startup/bootstrap/EnsureCreated/фоновые службы и файловый логгер не запускаются.

## Изоляция MySQL

Read-only preflight проверяет существующую test. Реквизиты из разрешённого AGENTS.md читаются в память, не передаются аргументом или в отчёты. Только TEMPORARY Users/UserTypes/ConnectedUsers/AdminPanelLogs одного удерживаемого соединения, pooling выключен. DROP всегда TEMPORARY; постоянные таблицы закрыты временными лишь в этом соединении. Состав постоянных таблиц сверяется до/после. Нет миграций, создания БД, очистки постоянных таблиц или записи файлов хранилища. Не запускать параллельные запросы через это соединение.

## Фактическое покрытие

17.10.2026: 1522 HTTP-утверждения, 521 запрос к тестовому серверу: 448 dispatch + 60 probe + 13 GET. Внутри HTTPS-прогона client.js выполнил 835 утверждений и 42 сетевые отправки: 40 AJAX-пар из исследования, нативный POST первоначального пароля и отдельный inline logout. Самостоятельный VM-прогон: 793 утверждения, без сети. Числа утверждений не являются числом независимых бизнес-сценариев.

client.js выполняет реальные send_data/send_file и тело inline logout, перехватывает XHR.open/setRequestHeader/send и FormData. В сетевом режиме только транспорт заменён синхронным Node HTTPS-мостом; сформированные помощниками заголовки/поля передаются в настоящий IAntiforgery. Для обычной HTML-формы используется hidden без AJAX-заголовка. Токены/cookie передаются в дочерний процесс только через stdin в памяти, не через файлы, URL или argv. Boundary назначает мост; прикладные помощники Content-Type не задают. Все 38 объявлений изменяющих форм проверяются на токен и явный POST; все 38 вызовов send_data исполняются отдельно. Из случайно содержащей токен GET-формы поле исключается из URL. Проверяются местный отказ при отсутствии meta, сохранение поведения HTTP-ошибок, отсутствие автоповтора и подавление двойного inline logout при всплытии submit.

HTTP-потоки проверяют настоящий HTML входа, первоначальной смены, CommonPage/UserTypes/UserProfile; hidden/meta, no-store, Secure/HttpOnly/Lax/Path/отсутствие Domain и Expires, HTTP→403 без выдачи cookie, отсутствие session-token/hash в HTML, анонимную пару/ошибку входа/новый вход/отзыв/обе смены пароля/профиль без смены/два набора токенов одной сессии/новый вход в другой вкладке/другую antiforgery-cookie. Старая пара после login не проходит probe; после logout/password с остаточной cookie может проходить по D09, но защищённый dispatch даёт 401. Криптографическая проверка пары не является авторизацией.

Для всех 41 пар передача проверена; полное успешное выполнение всех CRUD не проверяется. Защищённые операции с заголовком проверяются при низких правах, остальные сценарии сохраняют базовую матрицу HTTP 2.3.1 (1196 утверждений в исходном наборе). Без токена реальная мутация входа по-прежнему успешна: это намеренная граница 2.3.2.

## Осталось проверить

Настоящий браузер: DOM/Enter/requestSubmit/отказ JS/кеш/вкладки и Network, полный успешный CRUD/загрузки с файлами, Nginx/PathBase, реальные Data Protection keys и несколько экземпляров приложения. Замена XHR-транспорта не доказывает поведение браузерного multipart или DOM. HTTP-шлюз и HTML-формы не должны журналировать токены/пароли/cookies. После нового входа старой вкладке нужен ручной полный GET; обязательный отказ старого токена появится только в 2.3.3. До него CSRF-уязвимость не устранена.

## Регрессия F-01 (P3), 17.10.2026

`node tests/AdminAntiforgeryRegression/client-f01.js <исходный-корень-StoreCMS>`: 323 утверждения в 46 сценариях. Исполняются настоящие общие JS и inline logout. Проверяются отсутствующий и пустой meta, нулевая отправка и понятная локальная диагностика, сохранность полей/выбранного файла, отсутствие reload/повтора; отдельно исключение после начала send (даже с текстом прежней локальной ошибки), сетевой отказ, ошибка установки заголовка, HTTP-ошибки, неожиданный HTML и прежний успех. GET без meta сохраняет прежнюю работу. DOM/XHR моделируются; browser end-to-end не заявляется.

До исправления флаг `--expect-defect` подтвердил 48 утверждений в шести вариантах (3 отправителя x нет/пустой meta): send=0, одно неверное сообщение об неизвестном результате. Обычный режим нового теста на прежнем коде падает на проверке локального сообщения. После исправления прежние клиентские/HTTPS-наборы проходят без изменения количества их утверждений или сетевых отправок.

## Диагностика F-02 (P3), 17.10.2026

`node tests/AdminAntiforgeryRegression/client-f02.js <исходный-корень-StoreCMS>`: 152 утверждения в 32 сценариях. Исполняются реальные send_data, errorMsg/responseHandler и локальный обработчик кнопки Users. Проверяются все безопасные коды/сообщения, пустой/старый/повреждённый JSON, неизвестные и несовместимые со статусом коды, отказ отражать произвольный message из ответа, HTTP 400/401/403/409/500, сеть, отсутствие ложного успеха/повтора/reload, сохранение полей, X-CSRF-TOKEN и прежний 201. DOM/XHR моделируются; Opera остаётся ручной проверкой.

UserValidationChecks.cs добавляет реальные HTTP-сценарии в существующий безопасный host: admin2/admin → 422; неверные символы/длина/регистр запрещённого пароля; логин/пароль/роль/модель/ID отсутствуют или некорректны; роль не существует; занятый логин 409; профиль/IdleTime; успешные создание и редактирование роли. Корректный пароль проверен по фактическому хешу TEMPORARY-пользователя. Набор теперь даёт 1648 HTTP-утверждений / 545 запросов (471 dispatch, 60 probe, 14 GET). Все прежние 42 сетевые отправки и 835 клиентских утверждений сохранены.

Контракт только для AddUser, EditUser и EditUserData: известный 422 или занятый логин 409 получает JSON с единственным полем error. Значения: user_data_required, user_login_required, user_login_invalid, user_password_required, user_password_invalid, user_role_required, user_role_invalid, user_id_required, user_idle_time_invalid; для 409 только user_login_taken. Возвращается первая причина в прежнем порядке проверки. Никакие введённые значения, пароли, хеши, токены и исключения в JSON не включаются. Для отсутствующей модели AddUser/EditUser теперь есть явный 422 вместо обращения к null. Остальные 409 остаются общими конфликтами; пустой новый пароль профиля по-прежнему не меняет пароль.

Режим `--expect-f02` HTTP-хоста использовался с исходниками до исправления: подтвердил прежний пустой 422. Клиентский режим `--expect-f02` на сохранённом исходном helper подтвердил старое общее сообщение (5 утверждений). После исправления этот режим предназначен только для исходной копии; основной прогон выполняется без флага.

Для Opera обновить локальную сборку/перезапустить её обычным способом владельца и открыть Users заново. Проверить admin2/admin, свободный логин с допустимым паролем, занятый логин, пустые поля и профиль. Убедиться, что отказ не очищает поля и не перезагружает страницу. Ключ send_data.js?v=2.3.2-f02 на CommonPage/LoginForm/ChangeInitialPassword исключает прежний недельный кеш; успешный CRUD всех операций и полноценный browser end-to-end здесь не заявляются.
