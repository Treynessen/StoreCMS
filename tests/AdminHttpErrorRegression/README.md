# Регрессии HTTP-ошибок административной панели (2.3.1)

Проверяются реальные общие JavaScript-помощники и HTTPS Kestrel/MVC ASP.NET Core 2.2.8 с производственным AdminPanelController. Обязательная CSRF-валидация здесь не включается. При 2.3.2 VM-фикстура дополнена meta-токеном и setRequestHeader для совместимости с обновлёнными помощниками; все 3374 прежних утверждения сохранены. Новые проверки передачи находятся в ../AdminAntiforgeryRegression.

После исправления F-01 независимого ревью, 17.10.2026: **1196 HTTP-утверждений в 396 реальных запросах**, 3374 клиентских утверждения и 24 PasswordSecurityRegression прошли. Приложение, Razor и набор собраны в изолированной копии: 0 ошибок, 3 прежних предупреждения EOL/ForcedGC. Число утверждений не является числом независимых сценариев. Первоначальные 520 HTTP-утверждений не покрывали неизвестный pageID, что выявило независимое ревью. HTTP 500 и сетевые отказы проверяются клиентскими фикстурами; повреждение production-хранилища не выполняется.

Матрица F-01: POST/PUT/DELETE на /admin и /private/control-room; pageID=999, -1, 60, 0, переполнение Int32, отсутствующий, пустой и текстовый селектор. Без сессии ожидается 401; при высоких или низких правах с действительной сессией — 400. Для допустимых операций при низких правах остаётся 403. Для MainPage и других известных ID, отправленных неверным методом (включая Login/Exit/ChangeInitialPassword), — 400. Контролируются отсутствие Location и no-store. Отдельно проверены запрет HTTP (403), обязательная смена, обе успешные HTML-смены пароля с единственным намеренным LocalRedirect, отзыв, отказ старого пароля, повторный вход и идемпотентный выход на обоих маршрутах.

Новая регрессия была запущена в отдельной копии с серверным фильтром до исправления: expected 400 / actual 403. После восстановления исправленного фильтра набор проходит. Список SupportsAdminPanelMutation должен оставаться согласованным с ветками реальных диспетчеров; он только ограничивает допустимость метода/ID, а права по-прежнему проверяет HasAccessTo. Ошибки binding других полей не превращаются в общий 400: проверяются только PageId/model.PageId.

## Клиент

```powershell
node tests/AdminHttpErrorRegression/client.js
```

Нужен Node.js (без npm-пакетов). Набор читает вызовы из Razor: 38 изменяющих отправителей send_data, два PUT-загрузчика и отдельный выход с формы первоначального пароля. Дополнительно проверяет GET-помощник, реальные callback настроек/добавления роли, отсутствие callback/изменения страницы при 400/401/403/404/409/415/422/500, сетевом отказе, неожиданном статусе 2xx и HTML вместо ответа мутации. Проверяются синхронный XHR, preventDefault до отправки, сохранность полей, локальная валидация. DOM/XHR моделируются; это не браузерный end-to-end тест. Обычная HTML-форма смены пароля остаётся без изменения метода/маршрута.

## HTTP

Собирать в отдельной копии приложения и этого проекта без рабочего config.json, bin/obj/.vs. Пример из корня такой копии:

```powershell
dotnet restore tests/AdminHttpErrorRegression --configfile tests/AdminHttpErrorRegression/NuGet.Config -p:NuGetAudit=false -p:RestoreFallbackFolders="$env:USERPROFILE/.nuget/packages"
dotnet build tests/AdminHttpErrorRegression --no-restore
dotnet tests/AdminHttpErrorRegression/bin/Debug/netcoreapp2.2/AdminHttpErrorRegression.dll <исходный-корень-StoreCMS>
```

Реквизиты локальной существующей `test` на 127.0.0.1:3306 читаются в память из AGENTS.md исходного корня, не из config.json и не из аргументов. Сначала выполняется read-only preflight. Фикстуры создают только TEMPORARY Users/UserTypes/ConnectedUsers/AdminPanelLogs в одном удерживаемом MySQL-соединении. Все DbContext используют это соединение, HTTP-запросы последовательны, pooling выключен. Временные таблицы скрывают постоянные только в этом соединении; DROP всегда TEMPORARY. Постоянные таблицы, другие базы, миграции, настройки и файлы хранилища не изменяются. Сверяется состав постоянных таблиц до/после; закрытие соединения удаляет временные таблицы и при аварии.

Хост запускает реальные MVC-фильтры, model binding и контроллер на /admin и /private/control-room. Production Program/Startup, инициализация схемы, фоновые службы и production-логгер не запускаются. Одноразовый HTTPS-сертификат принимается только тестовым HttpClient. Проверяются все защищённые мутации без cookie (401 без Location), низкие права (403), реальный вход, идемпотентный выход, истечение сессии, 400 default и адресные бизнес-200/201/403/404/409/415/422. Не вызываются файловые операции или изменение настроек. Это адресная проверка HTTP-контракта, а не полный прогон успешного CRUD всех 41 операций.

## Контракт помощников

Для будущего воспроизводимого checkout необходимы все четыре локальных неотслеживаемых файла: send_data.js, send_file.js, insert_tab.js и checkbox_event_handler.js. Все они уже подключаются отслеживаемыми Razor-файлами в HEAD; без первых двух не работают отправки/загрузки, без последних нарушаются Tab в редакторах и передача изменённого значения checkbox. Файлы прочитаны полностью: встроенных секретов нет, синтаксис проверен Node; статическая копия Razor из HEAD с четырьмя файлами разрешает ссылки. Они допустимы для осознанного включения в будущий коммит. В рамках F-01 ни один из них не изменён и git add не выполнялся; полноценный запуск чистого checkout с production-настройками не проводился.

Первые четыре аргумента createSendDataEventHandler сохранены; пятый необязательный successStatus по умолчанию равен 200. Все 12 операций создания явно передают 201. responseHandler вызывается только для ожидаемого успешного статуса; HTTP-ошибки теперь централизованно показываются через showAdminPanelHttpError, поэтому прежние error-ветки смешанных responseHandler не используются. validationErrorHandler по-прежнему отвечает только за локальную валидацию. send_file сохраняет аргументы и расширения, требует 200 и использует общий диспетчер из send_data.js, подключённого CommonPage раньше содержимого раздела. Статусы сервера и бизнес-логика не подменяются клиентом.

Файлы send_data.js и send_file.js до шага были неотслеживаемыми, как insert_tab.js и checkbox_event_handler.js. В будущем включать в поставку осознанно только нужные файлы; массового git add Storage/scripts здесь нет. Версия ?v=2.3.1 на пяти script-src нужна из-за недельного Cache-Control статики: обе части общего контракта должны загружаться согласованно. Не меняются маршруты или методы HTML-форм.

До публикации остаются браузерные проверки реального кеша/Network, Enter/отказа JS, вкладок, HTML-формы первоначальной смены, Location успешного создания/переименования и Nginx/HTTPS. CSRF-токенов/заголовков/cookies пока нет, этап 2.3 не завершён.
